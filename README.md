# 인사 · 노무 · 세무 통합 관리 시스템

인사부터 근태, 노무, 4대보험, 기타소득, 세무, 교육까지를 하나의 사원 데이터 위에서 처리하는 관리 시스템. 학습 목적의 개인 프로젝트다.

현재 단계는 **요구사항 정의**다. 코드는 아직 없다.

## 왜 만드는가

인사 업무는 사원 데이터 하나가 근태, 급여, 4대보험, 세무, 교육으로 동시에 흘러간다. 그런데 현장에서는 각 단계가 서로 다른 엑셀 파일과 담당자에게 흩어져 있다. 입사 한 건이 발생하면 인사 등록, 근로계약서 작성, 4대보험 취득 신고, 법정교육 대상 지정을 각각 다른 도구에서 손으로 반복한다. 같은 값을 여러 번 입력하므로 어디선가 반드시 어긋나고, 법정 기한은 사람이 기억해야 한다.

사원 데이터를 한 번 입력하면 계약서와 신고 자료, 급여, 교육 대상 판정까지 자동으로 이어지고, 법정 기한은 시스템이 먼저 알리는 것이 목표다.

## 문서 구조

스펙 주도 개발(SDD)을 따른다. 기능 작업은 `specs/<NNN-slug>/` 아래 문서를 먼저 만들고, 코드는 그 문서를 근거로만 쓴다.

```
specs/
  000-product/        제품 수준 스펙 — 목표, 원칙, 도메인 지도, 확정 결정
  010-인사관리/        사원 마스터, 계약, 발령, 증명서
  020-근태관리/        근무시간 계산, 연차와 휴가, 마감
  030-노무관리/        취업규칙, 준수 검사, 징계, 안전보건
  040-보험관리/        4대보험 신고, 보험료 산정, 정산
  050-기타소득관리/    프리랜서·일용직 지급과 원천징수
  060-세무관리/        급여, 원천세, 연말정산, 퇴직소득
  070-교육운영관리/    법정의무교육 대상 판정과 이수 증빙
  900-플랫폼기반/      인증·권한, 전자결재, 알림, 배치, 감사
```

## 읽는 순서

1. **`specs/000-product/spec.md`** — 여기가 입구다. 제품 원칙 8개와 확정 결정 4개가 나머지 전부의 전제라, 이게 틀리면 아래 스펙도 같이 틀린다.
2. **`specs/900-플랫폼기반/spec.md`** — 도메인 스펙들이 "결재를 거쳐 승인된다", "권한 범위 안에서만 조회된다"고 쓸 때 그 실체가 여기 정의돼 있다.
3. 나머지 도메인은 관심 있는 순서대로 봐도 된다.

모든 기능 요구사항(FR)에 수용 기준(AC)이 1대1로 대응한다. 수용 기준은 EARS 문법으로 쓴다.

```
FR-002 사번은 채번 규칙에 따라 시스템이 자동 생성하고, 등록 이후 변경할 수 없어야 한다.
  AC-002 THE 시스템 SHALL 사번 수정 요청을 서비스 계층에서 거부하고,
         어떤 API 경로로도 사번이 바뀌지 않게 한다.
```

## 확정된 설계 결정

이 네 가지가 모든 도메인 스펙의 전제다. 하나가 바뀌면 하위 스펙도 함께 고쳐야 한다.

- **기간 제약 없음** — 단계별 기능 절단선을 두지 않는다. 스펙은 전 범위를 쓴다.
- **단일 기업 모델** — 회사 1개 아래 사업장과 부서. 대행 사무소 계층은 없다. 사업장을 계층으로 둔 이유는 4대보험 신고와 산재 요율이 사업장 단위이기 때문이다.
- **겸직 없음** — 사원은 사업장 1개, 부서 1개에만 소속된다. 소속 변경은 발령으로만 이루어진다.
- **급여는 060에 포함** — 별도 도메인을 두지 않는다.

## 아직 비어 있는 곳

**급여 계산 요구사항을 정의했다.** 060 세무관리의 5.6절에 지급 주기, 입력 스냅샷, 수당·일할·소급 계산, 보험료와 원천세 공제, 확정·정정, 이체·명세서와 평균임금 기초 데이터까지 연결한다.

제품 수준 열린 질문 5개(데이터베이스, 모바일 앱, 경비 청구, 기관 신고 방식, AI 모델)와 도메인별 질문 41개가 각 스펙에 남아 있다. 설계 문서(`design.md`) 착수 전까지 닫으면 된다.

## AI 에이전트와 함께 작업할 때

이 프로젝트는 여러 AI 도구로 같이 작업하는 것을 전제한다. 규칙은 **`AGENTS.md` 한 곳**에 있다.

- `AGENTS.md` — 공용 표준. Cursor, Codex, Copilot, Gemini CLI, Windsurf, Aider, Zed 등이 읽는다.
- `CLAUDE.md` — Claude Code는 AGENTS.md를 읽지 않아서 `@AGENTS.md` 한 줄로 불러온다.
- `.cursor/rules/spec-writing.mdc` — Cursor 전용. 스펙 문서를 편집할 때만 뜨는 확인 목록이다.

규칙을 고칠 때는 `AGENTS.md`만 고친다. 같은 내용을 여러 파일에 두면 갈라진다.

## 그 밖의 파일

- `archive-v1.0-요구사항정의서.md` — 병합 전 초안. 14개 모듈 122건 기준이라 현재 스펙과 구조가 다르다. 참고용으로만 남긴다.
- `build-canvas.py` — 스펙에서 요구사항을 추출해 Cursor 캔버스를 생성한다. 추출 건수가 원본과 다르면 실패하므로, 스펙을 고친 뒤 다시 돌리면 누락 여부까지 확인된다.
- `canvas/HR-ERP-requirements.canvas.tsx` — 320건을 도메인별로 접었다 펼쳐 보는 화면. **스펙에서 생성한 결과물이라 직접 고치지 않는다.** 스펙을 고쳤으면 아래를 다시 돌린다.

```
python3 build-canvas.py canvas/HR-ERP-requirements.canvas.tsx
```

Cursor에서 열려면 `~/.cursor/projects/<워크스페이스>/canvases/` 아래로 복사해야 한다. 저장소에 둔 사본은 공유와 열람용이다.
